# Проектирование ПО
# 1. Анализ требований и планирование проекта
## 1.1. Описание проблемы
Открытые данные и публичные реестры Росаккредитации позволяют проверить сертификаты и декларации соответствия, однако для прикладного пользователя поиск нужного документа остаётся сложной задачей. Пользователь часто располагает не точным номером документа, а фрагментом номера, описанием товара, названием заявителя, изготовителя или текстом из поставщицкого документа.

Основная проблема заключается в том, что пользователю необходимо быстро ответить на несколько вопросов: существует ли документ, действует ли он сейчас, относится ли он к конкретному товару и какую официальную ссылку можно использовать дальше. При этом ручной поиск может требовать переключения между разными реестрами, подбора фрагментов номера, проверки статуса, заявителя, изготовителя и описания продукции.

Разрабатываемая система должна упростить этот процесс за счёт нормализации пользовательского запроса, объединённого поиска по сертификатам и декларациям, гибридного поиска по структурированным и текстовым данным, а также объяснения найденных результатов с использованием RAG.
## 1.2 Цель проекта
Цель проекта — разработать backend-сервис для гибридного поиска сертификатов и деклараций соответствия по открытым данным Росаккредитации, позволяющий находить релевантные документы по неточному пользовательскому запросу, отображать их статус и ключевые реквизиты, а также формировать объяснение результата с использованием RAG и предоставлять инструменты поиска через MCP-интерфейс.

## 1.3 Задачи проекта 
1. Проанализировать предметную область сертификатов и деклараций соответствия.
2. Изучить структуру открытых данных Росаккредитации.
3. Спроектировать модель данных для хранения карточек документов, импортов и логов поиска.
4. Реализовать модуль загрузки, распаковки и парсинга открытых данных.
5. Реализовать REST API для поиска и просмотра документов.
6. Реализовать нормализацию пользовательских запросов.
7. Реализовать гибридный поиск: keyword search + vector search + metadata filters.
8. Реализовать RAG-модуль для объяснения найденных результатов.
9. Реализовать MCP-интерфейс для доступа LLM-клиентов к инструментам поиска.
10. Провести оценку качества поиска по выбранным метрикам.

## 1.4. Целевая аудитория
Целевой аудиторией сервиса являются специалисты, которым необходимо регулярно проверять сертификаты и декларации соответствия при работе с товарами, поставщиками и карточками товаров.

К потенциальным пользователям относятся:

- специалисты по сертификации;
- менеджеры небольших компаний-импортёров;
- сотрудники, готовящие карточки товаров для маркетплейсов;
- специалисты, проверяющие документы поставщиков.

В рамках MVP целевая аудитория сужается до специалиста по сертификации в небольшой компании-импортёре, так как именно у такого пользователя задача проверки документов возникает регулярно, а ошибка может привести к блокировке карточки товара, претензиям со стороны площадки или необходимости повторной проверки документов.

## 1.5 Основной пользователь системы
### *Специалист по сертификации в небольшой компании-импортёре, который готовит карточки товаров для маркетплейсов.*

Его сценарий:

1. Получил от поставщика номер документа, PDF, таблицу или описание товара.
2. Вводит фрагмент номера, название товара, модель, производителя или заявителя.
3. Сервис ищет сертификаты и декларации.
4. Пользователь открывает карточку.
5. Проверяет статус, сроки, заявителя, изготовителя и описание продукции.
6. Получает ссылку на источник.
7. При необходимости читает объяснение, почему документ подходит или не подходит.

## 1.6 Сценарии использования ПО 
### Сценарий 1. Поиск документа по номеру

Пользователь вводит:

```
ЕАЭС N RU Д-CN...
```

Система:
- нормализует номер;
- убирает лишние пробелы;
- учитывает возможную путаницу кириллицы и латиницы;
- ищет сертификаты и декларации;
- возвращает найденные документы.

### Сценарий 2. Поиск по описанию товара

Пользователь вводит:

```
детская хлопковая одежда для мальчиков
```

Система:

- делает семантический поиск по описанию продукции;
- применяет фильтры, если они есть;
- возвращает наиболее похожие документы.

### Сценарий 3. Поиск по заявителю или изготовителю

Пользователь вводит:
```
ООО Ромашка
```

Система ищет документы, где эта организация указана как заявитель или изготовитель.

### Сценарий 4. Проверка применимости документа

Пользователь открывает документ и спрашивает:
```
Подходит ли этот документ для детской одежды из хлопка?
```
Система:

- берёт найденную карточку;
- сравнивает товар пользователя с описанием продукции;
- формирует объяснение;
- показывает, какие поля совпали, а какие требуют ручной проверки.

### Сценарий 5. Получение результата через MCP

LLM-клиент вызывает инструмент:
```python
search_registry(query="детская одежда ООО Ромашка")
```
Сервис возвращает структурированный результат.


## 1.7 Состав MVP
MVP включает:
- импорт ограниченной выборки сертификатов и деклараций;
- хранение документов в PostgreSQL;
- обычный поиск по структурированным полям;
- нормализацию пользовательского запроса;
- семантический поиск по описанию продукции;
- карточку документа;
- RAG-объяснение результата;
- минимальный MCP-интерфейс с read-only tools.

## 1.8 Ограничения MVP
Что не входит:
- личный кабинет;
- роли пользователей;
- OCR PDF;
- загрузка пользовательских файлов;
- уведомления об изменении статуса;
- полноценная аналитика;
- промышленный внешний API;
- обучение собственной LLM;
- юридическое заключение.

## 1.9 Методология разработки
Для разработки применяется итеративно-инкрементальная методология. Система создаётся через последовательные версии: сначала реализуется базовый контур загрузки и структурированного поиска, затем добавляется гибридный поиск, далее RAG-объяснение, и на завершающем этапе MCP-интерфейс. Такой подход выбран из-за исследовательского характера проекта и необходимости проверять качество поиска на реальных данных.

# 2. Требования к программному обеспечению
## 2.1 Назначение системы
Разрабатываемая система предназначена для поиска сертификатов и деклараций соответствия по открытым данным Росаккредитации. Основная задача сервиса — помочь пользователю находить релевантные документы по неточным или неполным входным данным: фрагменту номера документа, описанию товара, названию заявителя, изготовителя или продукции.

Система должна объединять классический поиск по структурированным полям, семантический поиск с использованием векторной базы данных, а также RAG-подход для формирования объяснения найденных результатов. MCP-интерфейс используется как дополнительный слой интеграции, позволяющий LLM-клиентам обращаться к инструментам поиска сервиса.

Важно: система не является юридическим экспертом и не принимает окончательное решение о применимости документа. Она помогает пользователю быстрее найти официальный документ, увидеть его статус, ключевые поля и получить объяснение совпадения.

Основание для такой постановки есть в исследовании: главная проблема пользователя заключается не просто в открытии реестра, а в быстром ответе на вопросы: существует ли документ, действует ли он сейчас, относится ли он к конкретному товару и какую ссылку можно безопасно использовать дальше.

## 2.2 Функциональные требования
## 2.2.1 Импорт открытых данных

Система должна позволять импортировать данные сертификатов и деклараций из открытых наборов Росаккредитации.

### Описание

Система должна принимать путь к архиву или файлу с открытыми данными, распаковывать его, извлекать записи и сохранять их в базу данных.

### Критерии приемки
- Система может обработать тестовый архив или файл.
- После импорта в базе появляются записи документов.
- Для каждой записи сохраняется тип документа: сертификат или декларация.
- Для каждой записи сохраняются ключевые поля, если они присутствуют в исходных данных.
- Ошибочные записи не должны останавливать весь процесс импорта.

## 2.2.2 Хранение карточек документов

Система должна хранить сведения о сертификатах и декларациях в единой структуре данных.

### Минимальный набор полей
```
- id;
- document_type;
- document_number;
- status;
- applicant_name;
- manufacturer_name;
- product_name;
- product_description;
- technical_regulation;
- registered_at;
- valid_until;
- source_url;
- raw_data;
- search_text;
- created_at;
- updated_at.
```
### Критерии приемки
- Документы сертификатов и деклараций хранятся в одной таблице или в единой логической модели.
- Можно отличить сертификат от декларации.
- Можно получить документ по id.
- Можно получить документ по номеру.
- Исходные данные сохраняются в raw_data для последующей проверки и отладки.

## 2.2.3 Нормализация пользовательского запроса

Система должна выполнять предварительную обработку пользовательского запроса.

Что должна делать нормализация
- удалять лишние пробелы;
- приводить строку к единому регистру;
- очищать номер документа от лишних символов;
- учитывать возможную путаницу кириллицы и латиницы;
- выделять вероятный номер документа;
- выделять текстовую часть запроса для поиска по продукции.

### Пример

Ввод пользователя:
```
ЕАЭС N RU Д-CN.РА01.В.12345/23 детская одежда
```
Система должна понять, что в запросе есть:

- возможный номер документа;
- описание продукции: детская одежда.

### Критерии приемки
- Запрос с лишними пробелами обрабатывается корректно.
- Запрос с фрагментом номера не ломает поиск.
- Запрос с кириллицей и латиницей в похожих символах частично нормализуется.
- Исходный запрос и нормализованная версия сохраняются в лог поиска.

## 2.2.4 Классический поиск

Система должна выполнять поиск по структурированным полям документов.

Поля поиска
```
- номер документа;
- тип документа;
- статус;
- заявитель;
- изготовитель;
- наименование продукции;
- описание продукции;
- технический регламент;
- дата начала действия;
- дата окончания действия.
```
### Примеры запросов
```
GET /documents?document_type=declaration
GET /documents?status=active
GET /documents?applicant=ромашка
GET /documents?query=детская одежда
GET /documents?document_number=ЕАЭС
```
### Критерии приемки
- Пользователь может искать документы через REST API.
- Поиск поддерживает частичное совпадение по номеру.
- Поиск поддерживает частичное совпадение по названию заявителя.
- Поиск может быть ограничен типом документа.
- Поиск может быть ограничен статусом.
- Результаты возвращаются с пагинацией.
## 2.2.5 Семантический поиск

Система должна поддерживать семантический поиск по смыслу запроса.

### Описание

Для документов создаётся текстовое представление, например:
```
Тип документа: декларация.
Номер: ЕАЭС N RU ...
Статус: действует.
Заявитель: ООО Ромашка.
Изготовитель: ...
Продукция: одежда детская хлопковая.
Описание: ...
Технический регламент: ...
```
Для этого текста создаётся **embedding**, который сохраняется в векторной базе данных.

Пользовательский запрос также преобразуется в embedding. Затем система ищет документы, векторы которых ближе всего к вектору запроса.

### Критерии приемки
- Для документов можно сгенерировать embeddings.
- Embeddings сохраняются в базе.
- Пользователь может выполнить семантический поиск.
- Запрос “товары для малышей” может находить документы, где указана “детская продукция” или “одежда для детей”.
- В ответе возвращается similarity score или иной показатель релевантности.

## 2.2.6 Гибридный поиск

Система должна объединять классический и семантический поиск.

### Описание

Гибридный поиск должен использовать:

- точные и частичные совпадения по номеру;
- фильтры по типу документа и статусу;
- поиск по заявителю и изготовителю;
- семантический поиск по продукции и описанию;
- объединённое ранжирование результатов.
###Пример

Пользователь вводит:
```
действующая декларация на детскую одежду ООО Ромашка
```
Система должна:

1. Понять, что нужен тип документа: декларация.
2. Понять, что желательный статус: действует.
3. Искать организацию “ООО Ромашка”.
4. Семантически искать “детская одежда”.
5. Вернуть документы с объяснимым рейтингом.
### Критерии приемки
- Система возвращает общий список результатов.
- Результаты имеют итоговый score.
- В итоговом score учитываются структурные совпадения и семантическая близость.
- При точном совпадении номера документ должен попадать выше семантически похожих документов.
- При отсутствии точного номера система всё равно ищет по смыслу.

## 2.2.7 Карточка документа

Система должна отображать подробную карточку найденного документа.

Карточка должна содержать
```
- тип документа;
- номер документа;
- статус;
- срок действия;
- заявителя;
- изготовителя;
- наименование продукции;
- описание продукции;
- технический регламент;
- ссылку на источник;
- дату последнего обновления в системе;
- предупреждение о необходимости проверки официального источника.
```
### Критерии приемки
- Карточку можно получить по id.
- Карточка содержит ключевые реквизиты.
- Карточка содержит ссылку на источник, если она доступна.
- Пользователь видит дату последнего обновления данных.

## 2.2.8 RAG-объяснение результата

Система должна формировать объяснение найденных результатов с использованием RAG-подхода.

### Описание

RAG-модуль не должен искать данные самостоятельно. Он получает top-k документов из search service и формирует объяснение только на основе этих документов.

### Пример ответа
```
Найден документ, который может подходить под запрос.
Совпадения:
- тип продукции: указана детская одежда;
- заявитель: совпадает с ООО Ромашка;
- статус: документ действует.

Что требует ручной проверки:
- в описании не указана конкретная модель товара;
- необходимо сверить технический регламент и ссылку на официальный источник.
```
### Критерии приемки
- Ответ содержит объяснение совпавших полей.
- Ответ содержит предупреждение о ручной проверке.
- Ответ содержит ссылки или id документов-источников.
- Если документов не найдено, LLM не должна выдумывать результат.
- Если уверенность низкая, система должна явно сказать об этом.

## 2.2.9 MCP-интерфейс

Система должна предоставлять минимальный MCP-интерфейс для доступа к инструментам поиска.

### Минимальные MCP tools
1. search_registry
   Выполняет поиск по сертификатам и декларациям.

2. get_document_card
   Возвращает карточку документа по id или номеру.

3. explain_match
   Формирует объяснение соответствия документа запросу пользователя.

### Ограничения MCP
- MCP tools работают только на чтение.
- MCP tools не могут изменять базу данных.
- MCP tools не могут выполнять произвольный SQL.
- MCP tools не могут запускать команды операционной системы.
- Все вызовы MCP логируются.

### Критерии приемки
- MCP server запускается отдельно или вместе с backend.
- LLM-клиент может вызвать search_registry.
- LLM-клиент может получить карточку документа.
- Все MCP-инструменты имеют ограниченный набор параметров.

## 2.2.10 Логирование поиска

Система должна сохранять информацию о пользовательских поисковых запросах.

Что логировать
```
- исходный запрос;
- нормализованный запрос;
- выбранный режим поиска;
- количество найденных результатов;
- id документов в top-k;
- время выполнения поиска;
- был ли вызван RAG;
- дата и время запроса.
```
### Критерии приемки
- Каждый поисковый запрос сохраняется в лог.
- По логам можно понять, какие запросы были успешными.
- По логам можно рассчитывать базовые метрики качества поиска.

## 2.3 Нефункциональные требования
### 2.3.1 Производительность

Система должна обеспечивать приемлемое время ответа для учебного MVP.

### Требования
- обычный поиск должен выполняться не дольше 1–2 секунд на тестовой выборке;
- семантический поиск должен выполняться не дольше 2–5 секунд на тестовой выборке;
- RAG-ответ может выполняться дольше, но пользователь должен получать результат в разумное время;
- импорт данных может выполняться в фоновом или отдельном скриптовом режиме.
### 2.3.2 Масштабируемость

Система должна быть спроектирована так, чтобы в будущем можно было увеличить объём данных.

### Требования
- API не должен зависеть от фиксированного размера выборки;
- поиск должен поддерживать пагинацию;
- импорт должен обрабатывать данные батчами;
- embeddings должны создаваться пакетно;
- структура проекта должна позволять заменить pgvector на другую векторную базу данных при развитии проекта
### 2.3.3 Надёжность

Система не должна полностью прекращать работу из-за одной ошибочной записи.

### Требования
- ошибки парсинга отдельных записей должны логироваться;
- импорт должен продолжаться после некритичной ошибки;
- raw_data должен сохраняться для отладки;
- при ошибке LLM система должна вернуть найденные документы без объяснения;
- при ошибке семантического поиска должен оставаться доступен обычный поиск.
### 2.3.4 Проверяемость и объяснимость

Результаты поиска должны быть проверяемыми.

### Требования
- каждый результат должен содержать ключевые поля документа;
- каждый результат должен содержать ссылку на источник, если она доступна;
- RAG-ответ должен ссылаться на найденные документы;
- система должна показывать уровень уверенности или score;
- система должна явно отделять найденные факты от текстового объяснения LLM.
### 2.3.5 Безопасность

Так как система работает с открытыми данными, требования безопасности умеренные, но всё равно важные.

### Требования
- пользовательский ввод не должен попадать напрямую в SQL-запросы;
- все запросы к базе должны выполняться через ORM или параметризованные SQL-запросы;
- MCP-инструменты должны быть read-only;
- нельзя предоставлять пользователю возможность выполнить произвольный SQL;
- нельзя предоставлять LLM возможность изменять данные;
- внешние API-ключи должны храниться в .env, а не в коде.

### 2.3.6 Сопровождаемость

Код должен быть понятным и разделённым на слои.

### Требования
- API-роутеры не должны содержать сложную бизнес-логику;
- логика поиска должна быть вынесена в service layer;
- работа с базой должна быть вынесена в repository layer;
- настройки должны храниться в отдельном config-модуле;
- проект должен иметь README с инструкцией запуска.

### 2.3.7 Тестируемость

Система должна позволять проверить основные сценарии.

### Минимальные тесты
- тест нормализации номера документа;
- тест парсинга одной записи;
- тест создания search_text;
- тест обычного поиска;
- тест semantic search на небольшой выборке;
- тест RAG-ответа с mock LLM;
- тест MCP tool search_registry.

## 2.4. Требования к данным

Система должна работать с открытыми данными Росаккредитации, содержащими сведения о сертификатах и декларациях соответствия. В рамках MVP допускается использование ограниченной выборки данных, однако структура хранения должна позволять в дальнейшем увеличить объём импортируемых записей.

К данным предъявляются следующие требования:

- данные должны содержать сведения как минимум о сертификатах и декларациях соответствия;
- каждая запись должна иметь тип документа;
- по возможности должны сохраняться номер документа, статус, заявитель, изготовитель, описание продукции, срок действия и технический регламент;
- исходная запись должна сохраняться в поле raw_data для последующей проверки и отладки;
- для поисковых сценариев должно формироваться отдельное текстовое представление search_text;
- для семантического поиска по документу должен быть создан embedding;
- данные должны содержать дату импорта или обновления;
- система должна учитывать, что часть полей может отсутствовать или иметь неполный формат.

## 2.5. Требования к API

Система должна предоставлять REST API для взаимодействия с основными функциями сервиса. API должен позволять выполнять поиск документов, получать карточку документа, выполнять семантический и гибридный поиск, а также запрашивать RAG-объяснение.

К API предъявляются следующие требования:

- API должно быть реализовано с использованием FastAPI;
- API должно возвращать данные в формате JSON;
- поисковые запросы должны поддерживать пагинацию;
- параметры поиска должны передаваться через query parameters или тело POST-запроса;
- ошибки должны возвращаться в стандартизированном формате;
- API должно быть доступно для тестирования через Swagger UI;
- RAG endpoint должен возвращать не только текст ответа, но и список документов-источников;
- MCP-интерфейс должен предоставлять read-only tools для поиска и получения карточек документов.

## 2.6. Ограничения системы

Система имеет ряд ограничений, связанных с учебным характером проекта, источниками данных и использованием LLM.

Основные ограничения:

- система работает только с открытыми данными и публично доступными сведениями;
- система не использует закрытый API Росаккредитации;
- актуальность данных зависит от даты последнего импорта;
- система не выдаёт юридическое заключение о применимости документа;
- LLM используется только для объяснения найденных результатов, а не для генерации новых фактов;
- при отсутствии найденных документов система не должна формировать выдуманный ответ;
- MCP-инструменты работают только на чтение;
- в рамках MVP допускается работа с ограниченной выборкой документов;
- система не гарантирует полное покрытие всех документов Росаккредитации в демонстрационной версии.

## 2.7. Критерии приемки

MVP считается реализованным, если выполняются следующие условия:

- система запускается локально по инструкции из README;
- база данных PostgreSQL поднимается через Docker или локальное окружение;
- система может импортировать тестовую выборку сертификатов и деклараций;
- импортированные документы сохраняются в базе данных;
- пользователь может выполнить поиск по номеру документа;
- пользователь может выполнить поиск по заявителю или изготовителю;
- пользователь может выполнить поиск по описанию продукции;
- система возвращает карточку документа с ключевыми реквизитами;
- система поддерживает семантический поиск по текстовому запросу;
- гибридный поиск возвращает результаты с оценкой релевантности;
- RAG-модуль формирует объяснение на основе найденных документов;
- ответ RAG содержит ссылки или идентификаторы документов-источников;
- MCP-интерфейс предоставляет минимум один рабочий инструмент поиска;
- поисковые запросы логируются;
- основные сценарии покрыты тестами или ручными проверочными кейсами.

# 3. Архитектурное проектирование

## 3.1. Общая архитектура
Для реализации системы выбрана слоистая архитектура в рамках модульного монолита.

Приложение разрабатывается как единый backend-сервис, однако внутренняя структура проекта разделяется на несколько логических слоёв:
- API layer;
- service layer;
- repository layer;
- database layer;
- external services layer;
- MCP layer.
## 3.2. Модули системы
Система разделяется на несколько основных модулей.

### API module

Модуль отвечает за обработку HTTP-запросов пользователя.

В него входят:

- маршруты FastAPI;
- обработка query parameters и body parameters;
- возврат JSON-ответов;
- подключение Pydantic-схем;
- базовая обработка ошибок.

Примеры файлов:
```

app/api/search.py
app/api/rag.py
app/api/health.py
```
API module не должен содержать сложную бизнес-логику. Его задача — принять запрос, передать данные в service layer и вернуть результат пользователю.

### Schemas module

Модуль содержит Pydantic-схемы для валидации входных данных и формирования ответов API.

Примеры схем:

Этот модуль позволяет отделить внешний формат данных API от внутренней структуры базы данных.

Service layer содержит основную бизнес-логику системы.

В него входят:

- гибридное ранжирование;

Основные сервисы:
```

NormalizationService
EmbeddingService
RagService
```

Service module отвечает за то, что должна сделать система, но не должен напрямую содержать детали SQL-запросов или технические детали внешних API.

Основные репозитории:

Репозитории инкапсулируют SQL-запросы и операции с моделями SQLAlchemy. Благодаря этому service layer не зависит напрямую от деталей хранения данных.

Пример логики:

В него входят:

- компонент распаковки архивов;

Примеры компонентов:

MCP module предоставляет read-only инструменты для LLM-клиентов.

## 3.3. Схема взаимодействия модулей
Основной пользовательский сценарий — поиск документа по запросу.

Схема обработки поискового запроса:

1. Пользователь отправляет запрос в REST API.
2. API layer принимает запрос и валидирует входные параметры.
3. SearchService получает исходный запрос.
4. NormalizationService выполняет нормализацию запроса.
5. SearchService вызывает DocumentRepository для классического поиска.
6. SearchService вызывает EmbeddingService для получения embedding запроса.
7. DocumentRepository выполняет векторный поиск через pgvector.
8. SearchService объединяет результаты keyword search и vector search.
9. SearchService рассчитывает итоговый score.
10. SearchLogRepository сохраняет информацию о поиске.
11. API layer возвращает пользователю список найденных документов.

Схема:
```
Пользователь
    │
    ▼
FastAPI Router
    │
    ▼
SearchService
    │
    ├──► NormalizationService
    │
    ├──► DocumentRepository ───► PostgreSQL
    │
    ├──► EmbeddingService ─────► Embedding model
    │
    ├──► DocumentRepository ───► pgvector
    │
    └──► SearchLogRepository ─► PostgreSQL
    │
    ▼
JSON Response
```
Сценарий RAG-объяснения:

1. Пользователь отправляет вопрос в endpoint /ask.
2. API layer передаёт вопрос в RagService.
3. RagService вызывает SearchService для поиска top-k документов.
4. SearchService возвращает наиболее релевантные документы.
5. RagService формирует контекст для LLM.
6. LlmClient отправляет prompt в языковую модель.
7. RagService получает ответ модели.
8. RagService возвращает ответ и список документов-источников.

Схема:
```
Пользователь
    │
    ▼
RAG API
    │
    ▼
RagService
    │
    ├──► SearchService
    │        ├──► DocumentRepository
    │        └──► EmbeddingService
    │
    ├──► LlmClient
    │
    ▼
Ответ + источники
```
Сценарий MCP-вызова:

1. LLM-клиент вызывает MCP tool search_registry.
2. MCP layer принимает параметры инструмента.
3. MCP tool обращается к SearchService.
4. SearchService выполняет поиск через repository и embedding-сервисы.
5. MCP layer возвращает структурированный результат LLM-клиенту.

Схема:
```
LLM-клиент
    │
    ▼
MCP tool: search_registry
    │
    ▼
SearchService
    │
    ├──► NormalizationService
    ├──► DocumentRepository
    └──► EmbeddingService
    │
    ▼
Структурированный результат
```
Главный принцип взаимодействия модулей:
```
API layer и MCP layer не реализуют поиск самостоятельно. Они используют общие сервисы бизнес-логики.
```
Это снижает дублирование кода и делает поведение системы одинаковым независимо от способа обращения к ней.
## 3.4. Архитектурные решения по хранению данных
В качестве основного хранилища данных выбрана база данных PostgreSQL.

PostgreSQL используется для хранения:

- карточек сертификатов и деклараций;
- информации об импортах данных;
- логов поисковых запросов;
- текстовых представлений документов;
- векторных представлений документов.

Для поддержки семантического поиска используется расширение pgvector. Оно позволяет хранить embedding документа в PostgreSQL и выполнять поиск по близости векторов.

Такое решение выбрано по нескольким причинам:

- PostgreSQL хорошо подходит для backend-сервиса на FastAPI;
- структурированные данные и векторы можно хранить в одной базе;
- не требуется поднимать отдельную векторную базу данных;
- упрощается инфраструктура MVP;
- сохраняется возможность использовать SQLAlchemy и Alembic;
- pgvector можно заменить на отдельную vector database в будущем.
## 3.5. Архитектурные решения по поиску

Поиск в системе строится как гибридный retrieval, то есть сочетание нескольких подходов:

- нормализация пользовательского запроса;
- классический поиск по структурированным полям;
- keyword search по текстовым полям;
- vector search по embedding;
- metadata filtering;
- итоговое ранжирование результатов.

Такой подход выбран потому, что пользователь может вводить разные типы запросов:

- точный номер документа;
- фрагмент номера;
- название заявителя;
- название изготовителя;
- описание товара;
- смешанный запрос, где есть и организация, и товар, и статус.

Классический поиск хорошо работает, когда пользователь вводит точные или частично точные данные:

- номер документа;
- ИНН или название организации;
- статус;
- тип документа.

Семантический поиск полезен, когда пользователь вводит описание товара естественным языком:
```
товары для малышей
детская одежда
косметическая продукция
молочная продукция
```
Векторный поиск помогает находить документы, где текст отличается по словам, но близок по смыслу.

Например:

Запрос пользователя:
```
товары для малышей
```
Возможные релевантные документы:
```
детская одежда
изделия для новорождённых
продукция для детей
```
Общий алгоритм гибридного поиска:

1. Получить исходный запрос пользователя.
2. Выполнить нормализацию строки.
3. Попытаться выделить из запроса номер документа, тип документа, статус и организацию.
4. Выполнить классический поиск по структурированным полям.
5. Создать embedding пользовательского запроса.
6. Выполнить vector search по search_text документов.
7. Объединить результаты классического и векторного поиска.
8. Рассчитать итоговый score.
9. Отсортировать результаты по релевантности.
10. Вернуть top-k документов пользователю.

Пример факторов ранжирования:

- точное совпадение номера документа;
- частичное совпадение номера документа;
- совпадение типа документа;
- совпадение статуса;
- совпадение заявителя;
- совпадение изготовителя;
- keyword score;
- vector similarity score.

Приоритеты ранжирования:

1. Точное совпадение номера документа должно иметь наибольший вес.
2. Совпадение по заявителю или изготовителю повышает релевантность.
3. Совпадение по статусу и типу документа учитывается как metadata filter.
4. Семантическая близость влияет на результат при поиске по описанию товара.
5. Если точного номера нет, vector search помогает найти документы по смыслу.
## 3.6. Архитектурные решения по RAG и MCP
### RAG

RAG-модуль используется для формирования объяснения найденных результатов.

Важно, что LLM не должна самостоятельно искать документы или генерировать факты о сертификатах и декларациях. Она получает только те документы, которые уже были найдены search layer.

Общая схема RAG:

1. Пользователь задаёт вопрос.
2. SearchService находит top-k релевантных документов.
3. RagService формирует контекст из найденных документов.
4. LlmClient отправляет в LLM prompt с вопросом и контекстом.
5. LLM формирует объяснение только на основе переданных данных.
6. Пользователь получает ответ и список документов-источников.

В контекст для LLM передаются только ключевые поля:

- id документа;
- тип документа;
- номер документа;
- статус;
- заявитель;
- изготовитель;
- продукция;
- описание продукции;
- срок действия;
- технический регламент;
- source_url.

Пример задачи RAG:

Пользователь спрашивает:
```
Подходит ли найденный документ для детской хлопковой одежды?
```
Система должна ответить:
- какие поля совпали;
- какие поля не совпали;
- что требует ручной проверки;
- какой документ использовался как источник.

Ограничения RAG:

- LLM не должна выдумывать документы;
- LLM не должна изменять статус документа;
- LLM не должна давать юридическое заключение;
- при отсутствии найденных документов ответ должен явно сообщать, что данных недостаточно;
- ответ должен содержать ссылки или id документов-источников.

RAG в проекте используется не как самостоятельный “чат-бот”, а как объясняющий слой поверх результатов поиска.

### MCP

MCP-интерфейс используется как дополнительный способ доступа к функциям системы со стороны LLM-клиентов.

MCP layer предоставляет набор read-only инструментов:

search_registry
get_document_card
explain_match

Описание инструментов:
```
search_registry
Выполняет поиск по сертификатам и декларациям.
Принимает текстовый запрос и дополнительные фильтры.
Возвращает список релевантных документов.

get_document_card
Возвращает подробную карточку документа по id или номеру документа.

explain_match
Формирует объяснение применимости документа к пользовательскому запросу.
Использует RagService и найденные документы.
```

MCP-инструменты не должны обращаться к базе данных напрямую. Они используют service layer:
```
MCP tool
   ↓
SearchService / RagService
   ↓
Repository Layer
   ↓
Database
```

Ограничения MCP:

- только чтение данных;
- отсутствие произвольного SQL;
- отсутствие команд операционной системы;
- отсутствие изменения документов;
- логирование вызовов;
- ограниченный набор параметров.

Такой подход делает MCP безопасной интеграционной прослойкой, а не отдельной бизнес-логикой.

### 3.7.4 Реализация классического и семантического поиска

Для реализации классического и семантического поиска используются:

```
- PostgreSQL filters;
- ILIKE / full-text search / pg_trgm;
- pgvector;
- sentence-transformers или embedding API российской LLM-платформы.
```

Классический поиск выполняется средствами PostgreSQL по структурированным полям и текстовым значениям. Для частичного поиска могут использоваться ILIKE, полнотекстовый поиск PostgreSQL или расширение pg_trgm.

Для семантического поиска используются embeddings — векторные представления текстового описания документа. Embeddings могут создаваться локально с помощью моделей sentence-transformers либо через API российских LLM-платформ, например GigaChat Embeddings или YandexGPT Embeddings. Выбранная реализация инкапсулируется в компоненте EmbeddingClient, что позволяет заменить модель embeddings без изменения основной логики поиска.

### 3.7.5 LLM и RAG
Для формирования объяснений используется RAG-модуль и языковая модель.

Возможные варианты LLM:

- GigaChat API;
- YandexGPT API;
- локальная LLM через Ollama.

В рамках проекта предпочтение отдаётся российским LLM-платформам, так как система работает с русскоязычными открытыми данными Росаккредитации и должна формировать объяснения на русском языке.

LLM используется только для объяснения результатов, найденных поисковым модулем. Модель не должна самостоятельно выдумывать документы, изменять статусы или давать юридические заключения. В архитектуре обращение к языковой модели инкапсулируется в компоненте LlmClient. Это позволяет заменить конкретного провайдера, например GigaChat API на YandexGPT API или локальную модель, без изменения RAG-сервиса.

| Номер протокола ИЛ        | Номер протокола ИЛ      | Номер протокола ИЛ            |

---

Из этого следует, что сертификаты и декларации можно хранить в единой таблице документов, различая их по типу документа.

Такое решение удобно для проекта, потому что пользователь системы должен выполнять единый поиск по сертификатам и декларациям, а не работать с двумя полностью разными наборами данных.

### 4.1.4. Особенности исходных данных
При анализе примеров были выявлены следующие особенности данных.
### Наличие пустых значений

Во многих строках часть полей может быть пустой. Например, не всегда заполнены:
```
Номер ГТД
Глобальный номер GTIN
Модель
Артикул
Сорт
Дата приостановки
Дата прекращения
Дата возобновления
```
Поэтому большинство полей в таблице документов должны допускать значение NULL.
### Разные названия одинаковых по смыслу полей
Например:
```
Полное наименование
Полное наименование продукции
```
В базе данных такие поля целесообразно привести к единому названию, например:
```
product_full_name
```
Другой пример:

```
Торговая марка
Марка продукции
```
В единой модели это можно хранить как:
```
product_brand
```
### Наличие множественных значений в одном поле
Некоторые поля могут содержать несколько значений, записанных через разделитель.
Например:
```
Тех регламенты
Коды ОКПД2 / ТНВЭД
Номер протокола ИЛ
Дата протокола ИЛ
```
В MVP такие значения можно хранить строкой, так как основная задача проекта — поиск и отображение документа. В дальнейшем эти данные можно вынести в отдельные связанные таблицы.

### Разные форматы дат
В данных могут встречаться разные форматы дат, например:
```
29.08.2025
2025-08-22
```
Поэтому на этапе импорта необходима нормализация дат перед сохранением в базу данных.

### Наличие специфичных полей

Некоторые поля характерны только для сертификатов или только для деклараций.

Например, для сертификатов:
```
Номер бланка
Номер бланка приложений
Срок следующего ИК
Рег номер серт
Номер СМК
```
Для деклараций:
```
Тип декларанта
Номер серт на тип прод
Серт соотв СМК
Зарег Заявителем (СРД)
Статус исследований
```
Такие поля не всегда нужны для основных сценариев поиска. Поэтому в MVP часть специфичных полей можно хранить в исходном виде в поле raw_data.

## 4.2. Выделение основных сущностей
На основе анализа исходных данных и требований к системе были выделены основные сущности, которые необходимо хранить в базе данных.

1. Документ реестра
2. Импорт данных
3. Векторное представление документа
4. Поисковый запрос
5. Результат поисковой выдачи

### 4.2.1. Документ реестра
Сущность «Документ реестра» представляет сертификат или декларацию соответствия, полученные из открытых данных Росаккредитации.

Документ реестра является центральной сущностью системы.

Он содержит:

- тип документа;
- номер документа;
- статус;
- дату регистрации;
- срок действия;
- сведения о заявителе;
- сведения об изготовителе;
- сведения о продукции;
- технические регламенты;
- коды продукции;
- сведения об испытательной лаборатории;
- исходную строку данных;
- текстовое представление для поиска.

Документ реестра используется:
- в классическом поиске;
- в семантическом поиске;
- в карточке результата;
- в RAG-объяснении;
- в MCP-инструментах.
### 4.2.2. Импорт данных
Сущность «Импорт данных» описывает процесс загрузки и обработки файла с открытыми данными.

Она нужна для контроля происхождения данных и отслеживания актуальности.

Импорт данных содержит:

- имя исходного файла;
- тип импортируемых документов;
- дату начала импорта;
- дату завершения импорта;
- статус импорта;
- количество обработанных строк;
- количество успешно загруженных записей;
- количество ошибок.

Эта сущность важна, потому что данные Росаккредитации загружаются из выгрузок, и пользователь должен понимать, когда информация была обновлена в системе.
### 4.2.3. Векторное представление документа
Сущность «Векторное представление документа» хранит embedding документа.

Embedding — это числовое представление текстового описания документа, которое используется для семантического поиска.

Векторное представление создаётся не из исходных данных напрямую, а из подготовленного текстового поля `search_text`.

Например, в `search_text` могут входить:
```
тип документа,
номер документа,
статус,
заявитель,
изготовитель,
описание продукции,
торговая марка,
модель,
коды продукции,
технические регламенты.
```
Векторное представление является производным значением. Поэтому его удобно хранить отдельно от основной карточки документа.

### 4.2.4. Поисковый запрос

Сущность «Поисковый запрос» описывает запрос, который пользователь отправляет в систему.

Она нужна для логирования и дальнейшей оценки качества поиска.

Поисковый запрос содержит:
- исходный текст запроса;
- нормализованный текст запроса;
- режим поиска;
- применённые фильтры;
- количество найденных результатов;
- время выполнения запроса;
- признак использования RAG.

Такая информация позволяет анализировать работу поиска и рассчитывать метрики качества.

### 4.2.5. Результат поисковой выдачи
Сущность «Результат поисковой выдачи» описывает связь между поисковым запросом и документами, которые были возвращены пользователю.

Она содержит:
```
- ссылку на поисковый запрос;
- ссылку на найденный документ;
- позицию документа в выдаче;
- оценку keyword search;
- оценку vector search;
- итоговую оценку релевантности;
- поля, по которым произошло совпадение.
```
Эта сущность нужна не только для логирования, но и для оценки качества поиска, например Precision@k и MRR.

## 4.4. Связи между таблицами
Между таблицами используются следующие связи:
```
import_batches 1 → N registry_documents
registry_documents 1 → N document_embeddings
search_logs 1 → N search_log_results
registry_documents 1 → N search_log_results
```
Описание связей:

1. Один импорт может содержать много документов.
2. Один документ может иметь одно или несколько векторных представлений.
3. Один поисковый запрос может иметь несколько результатов выдачи.
4. Один документ может встречаться в результатах разных поисковых запросов.

Схематично связи можно представить так:
```
import_batches
      │
      │ 1:N
      ▼
registry_documents
      │
      │ 1:N
      ▼
document_embeddings


search_logs
      │
      │ 1:N
      ▼
search_log_results
      ▲
      │ N:1
      │
registry_documents
```
Таблица search_log_results является связующей между поисковым запросом и найденными документами.

## 4.5. Особенности хранения и поиска данных
### 4.5.1. Хранение исходных данных
Для каждой записи документа сохраняется исходная строка данных в поле `raw_data`.

Поле `raw_data` необходимо по следующим причинам:

1. В исходных файлах много полей, и не все они нужны в отдельных колонках MVP.
2. Некоторые поля специфичны только для сертификатов или только для деклараций.
3. При ошибках импорта можно проверить исходное значение.
4. В будущем можно расширить модель данных без повторной загрузки исходного файла.

Для хранения `raw_data` целесообразно использовать тип `JSONB` PostgreSQL.

### 4.5.2. Формирование поискового текста
Для семантического поиска и RAG в таблице документов формируется поле `search_text`.

Оно представляет собой текстовое описание документа, собранное из наиболее важных полей.

Пример `search_text`:
```
Тип документа: сертификат.
Номер документа: ЕАЭС RU С-CN.АЯ46.В.27677/23.
Статус: Архивный.
Заявитель: Общество с ограниченной ответственностью "ЛЮКС ТРЕЙД".
Изготовитель: MCSTYLES TRADE CO. LIMITED.
Продукция: Одежда верхняя для девочек старше 3 лет.
Коды продукции: 6204329000; 6204420000.
Технические регламенты: О безопасности продукции, предназначенной для детей и подростков.
Испытательная лаборатория: RA.RU.21АЗ43.
```
Поле `search_text` используется:
- для keyword search;
- для создания embedding;
- для формирования RAG-контекста;
- для отладки поисковой выдачи.


### 4.5.3. Хранение векторных представлений
Для семантического поиска по смыслу используются embeddings.

Embedding хранится в таблице `document_embeddings` и связан с документом через `document_id`.

Такое хранение позволяет отделить исходные данные от производных данных, созданных AI-моделью.

При изменении модели embeddings можно пересоздать записи в `document_embeddings`, не изменяя таблицу `registry_documents`.

## 4.6. Возможности расширения базы данных
В MVP используется упрощённая модель данных. Она выбрана для того, чтобы не усложнять импорт и быстрее реализовать работающий поиск.

В дальнейшем модель можно расширить.

Возможные направления расширения:

1. Вынести заявителей и изготовителей в отдельную таблицу `organizations`.
2. Вынести продукцию в отдельную таблицу `products`.
3. Вынести технические регламенты в таблицу `technical_regulations`.
4. Вынести коды ОКПД2 и ТНВЭД в отдельную таблицу `product_codes`.
5. Вынести испытательные лаборатории в отдельную таблицу `test_laboratories`.
6. Добавить таблицу `document_status_history` для хранения истории изменения статусов.
7. Добавить таблицу `rag_answers` для хранения ответов RAG-модуля.

На этапе MVP эти сущности не выносятся отдельно по следующим причинам:

1. В исходных данных много текстовых и неполных значений.
2. Организации и изготовители могут быть записаны в разных форматах.
3. Один документ может относиться к группе продукции, а не к одному товару.
4. Технические регламенты и коды продукции часто записаны несколькими значениями в одном поле.
5. Излишняя нормализация усложнит импорт и увеличит срок разработки.

Поэтому для MVP выбран компромиссный вариант: основные поисковые поля хранятся в отдельных колонках, а полная исходная запись сохраняется в `raw_data`.

Такой подход позволяет реализовать основные функции проекта и при этом оставить возможность дальнейшего развития базы данных.

# 5. Проектирование API

## 5.1. Назначение API
API предназначено для взаимодействия внешних клиентов с backend-сервисом поиска сертификатов и деклараций соответствия.

Через API пользователь или клиентское приложение может:

- проверить работоспособность сервиса;
- получить карточку документа;
- выполнить поиск по сертификатам и декларациям;
- выполнить гибридный поиск по неточному запросу;
- получить RAG-объяснение найденных результатов;
- запустить импорт данных в административном режиме;
- получить информацию о выполненных импортах.

В системе предусматриваются два типа интерфейсов:

1. REST API
   Основной интерфейс для взаимодействия с backend-сервисом.

2. MCP tools
   Интерфейс для LLM-клиентов, позволяющий вызывать инструменты поиска и получения карточек документов.

REST API используется для работы приложения, тестирования через Swagger UI и интеграции с возможным frontend. MCP-интерфейс используется как дополнительный слой для подключения LLM-клиентов к функциям сервиса.

Важно, что REST API и MCP tools не должны содержать отдельную бизнес-логику. Они обращаются к общим сервисам приложения: `SearchService`, `RagService`, `ImportService` и другим компонентам service layer.

### 5.2.4. RAG API
RAG API предназначено для формирования объяснения найденных результатов с использованием языковой модели.

Важно: RAG API не должен использовать LLM как самостоятельный источник фактов. Сначала система выполняет поиск документов, а затем передаёт найденные документы в LLM как контекст.

### Endpoint
```
POST /rag/ask
```
### Назначение

Принимает вопрос пользователя, выполняет поиск релевантных документов и формирует объяснение на основе найденных результатов.

### Пример запроса
```JSON
{
  "question": "Подходит ли эта декларация для детской хлопковой одежды?",
  "document_id": 125
}
```

Возможен и другой вариант запроса, когда документ заранее не выбран:
```JSON
{
  "question": "Найди действующие документы на детскую хлопковую одежду ООО Ромашка",
  "limit": 5
}
```
### Пример ответа
```JSON
{
  "answer": "Найден документ, который может соответствовать запросу. Совпадает тип продукции: в описании указана детская хлопковая одежда. Также совпадает заявитель: ООО Ромашка. Статус документа — Действует. При этом необходимо вручную проверить модель товара и технический регламент.",
  "confidence": "medium",
  "sources": [
    {
      "id": 125,
      "document_type": "declaration",
      "document_number": "ЕАЭС N RU Д-CN.РА01.В.12345/23",
      "status": "Действует",
      "product_full_name": "Одежда детская хлопковая"
    }
  ],
  "warnings": [
    "Ответ не является юридическим заключением.",
    "Необходимо сверить данные с официальным источником."
  ]
}
```
### Коды ответа
```
200 — ответ сформирован;
400 — вопрос пустой или некорректный;
404 — документ или релевантные документы не найдены;
503 — LLM-сервис временно недоступен;
500 — внутренняя ошибка сервера.
```
### Ограничения RAG API

- LLM не должна выдумывать документы;
- LLM не должна изменять статус документа;
- LLM не должна давать юридическое заключение;
- ответ должен основываться только на найденных документах;
- ответ должен содержать источники;
- при недостатке данных система должна явно сообщить об этом.
### 5.2.5. Import API
Import API предназначено для административного запуска импорта данных.

Так как импорт открытых данных может быть ресурсоёмкой операцией, данный API не предназначен для обычного пользователя. Он должен использоваться только в административном или локальном режиме.

В рамках MVP импорт может запускаться двумя способами:

1. Через отдельный скрипт.

Автоматический запуск импорта по расписанию рассматривается как возможность расширения. Например, отдельный скрипт или планировщик может периодически вызывать административный endpoint импорта.

### Получение списка импортов
```
GET /admin/imports
```

### Назначение

Возвращает список выполненных импортов.

### Пример ответа

Для учебного MVP можно реализовать импорт сначала через скрипт, а административный endpoint добавить после того, как будет готов и протестирован `ImportService`.

В MVP предусматриваются три инструмента:

## 5.6. Ограничения API
API имеет следующие ограничения:

- API не предоставляет юридических заключений;
- API не изменяет официальные данные Росаккредитации;
- документы импортируются из открытых данных и хранятся в локальной базе;
- актуальность данных зависит от даты последнего импорта;
- RAG API отвечает только на основе найденных документов;
- MCP tools работают только на чтение;
- Import API должен быть доступен только в административном режиме;
- автоматический импорт по расписанию не является обязательной частью MVP.

В рамках MVP основным способом загрузки данных является ручной запуск импорта через скрипт или административный endpoint. Автоматический импорт по расписанию рассматривается как направление развития системы, так как требует дополнительной обработки ошибок, контроля состояния задач и защиты административных операций.

Для MVP приоритетной является реализация следующих endpoint-ов:
```
GET /health
GET /documents/{document_id}
POST /search
POST /rag/ask
POST /admin/imports
GET /admin/imports/{import_id}
```
Остальные endpoint-ы могут быть добавлены после реализации основной логики поиска и импорта.

# 6. Проектирование поиска и RAG
## 6.1. Общая схема поиска
Поиск является центральной функцией разрабатываемой системы. Основная задача поискового модуля — находить релевантные сертификаты и декларации соответствия по неточному или неполному пользовательскому запросу.

Пользователь может вводить разные типы данных:

- полный номер документа;
- фрагмент номера документа;
- название заявителя;
- название изготовителя;
- ИНН или ОГРН организации;
- описание продукции;
- торговую марку;
- модель;
- код продукции;
- смешанный запрос из нескольких признаков.

Поэтому в системе используется не один способ поиска, а комбинация нескольких подходов:

1. Нормализация пользовательского запроса.
2. Классический поиск по структурированным полям.
3. Семантический поиск по векторным представлениям.
4. Гибридное ранжирование результатов.
5. RAG-объяснение найденных документов.

Общая схема поиска:
```
Пользовательский запрос
        ↓
Нормализация запроса
        ↓
Выделение признаков: номер, статус, тип документа, организация, текст продукции
        ↓
Классический поиск
        ↓
Семантический поиск
        ↓
Объединение результатов
        ↓
Гибридное ранжирование
        ↓
Возврат top-k документов
        ↓
RAG-объяснение, если оно запрошено пользователем
```
Важный принцип системы:
```
LLM не используется для непосредственного поиска документов в базе. Сначала документы находятся поисковым модулем, и только после этого LLM формирует объяснение на основе найденных данных.
```
Такой подход снижает риск генерации недостоверных ответов и делает результат проверяемым.
## 6.2. Нормализация пользовательского запроса
Нормализация запроса — это предварительная обработка текста, введённого пользователем.

Она необходима потому, что пользователь может вводить данные в неточном виде:

- с лишними пробелами;
- с разным регистром букв;
- с частичным номером документа;
- с ошибками в символах;
- с перемешанными русскими и латинскими буквами;
- с несколькими признаками в одной строке.

Пример пользовательского запроса:
```
ЕАЭС N RU Д-CN.РА01.В.12345/23 детская одежда ООО Ромашка
```
В таком запросе одновременно присутствуют:

- возможный номер документа;
- описание продукции;
- название организации.

Задача нормализации — привести запрос к виду, удобному для дальнейшего поиска.

### Основные операции нормализации

В рамках MVP нормализация включает следующие шаги:

1. Удаление лишних пробелов.
2. Приведение строки к единому регистру.
3. Удаление лишних служебных символов.
4. Нормализация похожих символов кириллицы и латиницы.
5. Выделение возможного номера документа.
6. Определение типа документа по словам “сертификат”, “декларация”, “ДС”, “СС”.
7. Определение желаемого статуса по словам “действующий”, “архивный”, “приостановлен”.
8. Выделение текстовой части запроса для поиска по продукции.

Пример результата нормализации:
```JSON
{
  "original_query": "ЕАЭС N RU Д-CN.РА01.В.12345/23 детская одежда ООО Ромашка",
  "normalized_query": "еаэс n ru д-cn.ра01.в.12345/23 детская одежда ооо ромашка",
  "document_number_candidate": "ЕАЭС N RU Д-CN.РА01.В.12345/23",
  "document_type_candidate": "declaration",
  "status_candidate": null,
  "text_query": "детская одежда ооо ромашка"
}
```
### Нормализация кириллицы и латиницы

В номерах сертификатов и деклараций могут встречаться похожие символы кириллицы и латиницы.

Например:
```
А / A
В / B
Е / E
К / K
М / M
Н / H
О / O
Р / P
С / C
Т / T
Х / X
```
Из-за этого пользователь может ввести часть номера латиницей, хотя в данных используется кириллица, или наоборот.

Для повышения устойчивости поиска можно формировать дополнительное нормализованное представление номера документа, в котором похожие символы приводятся к единому виду.

Пример:
```
Исходный номер:
ЕАЭС N RU Д-CN.РА01.В.12345/23

Нормализованное представление:
EAEC N RU D-CN.PA01.B.12345/23
```
В MVP такую нормализацию можно реализовать частично, только для наиболее частых символов.

### Результат нормализации

После нормализации поисковый модуль получает несколько полезных частей запроса:

- исходный запрос;
- нормализованный запрос;
- возможный номер документа;
- возможный тип документа;
- возможный статус;
- текстовую часть для keyword search;
- текстовую часть для semantic search.

Эти данные далее используются в классическом, семантическом и гибридном поиске.
## 6.3. Классический поиск
Классический поиск используется для поиска по точным или частичным совпадениям в структурированных полях базы данных.

Он особенно полезен, когда пользователь вводит:

- номер документа;
- фрагмент номера документа;
- ИНН заявителя;
- ОГРН заявителя;
- название заявителя;
- название изготовителя;
- код продукции;
- статус документа;
- тип документа.

Классический поиск выполняется по таблице `registry_documents`.

### Поля для классического поиска

Основные поля:
```
document_number
status
document_type
applicant_name
applicant_inn
applicant_ogrn
manufacturer_name
manufacturer_inn
manufacturer_ogrn
product_codes
product_full_name
product_brand
product_model
product_article
technical_regulations
```
### Примеры классического поиска
#### Поиск по номеру документа
Пользователь вводит:
```
ЕАЭС N RU Д-CN.РА01.В.12345/23
```
Система ищет совпадения по полю:
```
document_number
```
При точном совпадении документ должен иметь максимальный приоритет в выдаче.

### Поиск по фрагменту номера
Пользователь вводит:
```
12345/23
```
Система выполняет частичный поиск по номеру документа.

Это важно, потому что пользователь не всегда вводит полный номер сертификата или декларации.

### Поиск по заявителю
Пользователь вводит:
```
ООО Ромашка
```
Система ищет совпадения по полям:
```
applicant_name
manufacturer_name
```
При необходимости поиск может дополнительно учитывать ИНН и ОГРН.

### Поиск по продукции
Пользователь вводит:
```
детская одежда
```
Система ищет совпадения по полям:
```
product_full_name
product_designation
product_type
product_brand
product_model
product_article
search_text
```
### Преимущества классического поиска
1. Хорошо работает с точными значениями.
2. Позволяет использовать фильтры.
3. Быстро выполняется на структурированных данных.
4. Удобен для поиска по номеру, ИНН, ОГРН и статусу.
### Ограничения классического поиска
1. Плохо работает с неточными описаниями товара.
2. Не понимает смысловые совпадения.
3. Может не найти документ, если пользователь использует другие слова.
4. Чувствителен к ошибкам и разным формам написания.

Например, запрос:
```
товары для малышей
```
может не найти документы, где написано:
```
одежда для детей
```
Для решения этой проблемы используется семантический поиск.
## 6.4. Семантический поиск
Семантический поиск используется для поиска документов по смыслу пользовательского запроса.

Он основан на использовании embeddings — векторных представлений текста.

### Формирование поискового текста

Для каждого документа формируется поле `search_text`.

Оно собирается из наиболее важных полей карточки документа:

- тип документа;
- номер документа;
- статус;
- заявитель;
- изготовитель;
- полное наименование продукции;
- обозначение продукции;
- тип продукции;
- торговая марка;
- модель;
- артикул;
- коды продукции;
- технические регламенты;
- испытательная лаборатория.

Пример `search_text`:
```
Тип документа: декларация.
Номер документа: ЕАЭС N RU Д-CN.РА01.В.12345/23.
Статус: Действует.
Заявитель: ООО Ромашка.
Изготовитель: Example Manufacturing Co. Ltd.
Продукция: одежда детская хлопковая.
Торговая марка: Example Brand.
Модель: Model A.
Коды продукции: 6204420000.
Технические регламенты: О безопасности продукции, предназначенной для детей и подростков.
```
Создание embeddings

Для каждого `search_text` создаётся embedding.

Общий процесс:

1. Из таблицы registry_documents берётся search_text.
2. EmbeddingClient передаёт текст в embedding-модель.
3. Модель возвращает числовой вектор.
4. Вектор сохраняется в таблице document_embeddings.
5. Документ становится доступным для vector search.

Embedding может создаваться:

- локальной моделью;
- российской LLM-платформой через API;
- другой embedding-моделью, выбранной для MVP.

Конкретная модель инкапсулируется в компоненте `EmbeddingClient`, чтобы её можно было заменить без изменения логики поиска.

### Выполнение семантического поиска

При пользовательском запросе выполняются следующие шаги:

1. Запрос нормализуется.
2. Из запроса выделяется текстовая часть.
3. Для текстовой части создаётся embedding.
4. С помощью pgvector выполняется поиск ближайших document_embeddings.
5. Возвращаются документы с наибольшей смысловой близостью.

Пример:

Пользовательский запрос:
```
товары для малышей
```
Семантически похожие документы:
- одежда для детей;
- изделия для новорождённых;
- продукция для детей и подростков.
### Преимущества семантического поиска
1. Позволяет искать по смыслу, а не только по точным словам.
2. Устойчивее к неточным описаниям товара.
3. Подходит для пользовательских запросов на естественном языке.
4. Хорошо дополняет классический поиск.
### Ограничения семантического поиска
1. Не гарантирует точного юридического соответствия документа товару.
2. Может находить похожие, но не полностью подходящие документы.
3. Требует создания embeddings для документов.
4. Качество зависит от выбранной embedding-модели.

Поэтому семантический поиск используется не отдельно, а вместе с классическим поиском и фильтрами.
## 6.5. Гибридное ранжирование
Гибридное ранжирование объединяет результаты классического и семантического поиска.

Это нужно, потому что разные типы запросов требуют разных способов оценки релевантности.

Например:

- если пользователь ввёл точный номер документа, важнее классический поиск;
- если пользователь ввёл описание товара, важнее семантический поиск;
- если пользователь ввёл смешанный запрос, нужно учитывать оба подхода.

### Компоненты оценки релевантности

Для каждого найденного документа могут рассчитываться несколько оценок:
```
keyword_score
vector_score
metadata_score
final_score
```

#### keyword_score

`keyword_score` показывает, насколько хорошо документ совпал с запросом по текстовым и структурированным полям.

На него могут влиять:

- точное совпадение номера документа;
- частичное совпадение номера документа;
- совпадение заявителя;
- совпадение изготовителя;
- совпадение ИНН или ОГРН;
- совпадение кода продукции;
- совпадение слов в описании продукции.
#### vector_score

`vector_score` показывает смысловую близость запроса и документа.

Он рассчитывается на основе результата vector search через pgvector.

Чем выше смысловая близость, тем выше `vector_score`.

#### metadata_score

`metadata_score` учитывает совпадение дополнительных фильтров:

- тип документа;
- статус;
- срок действия;
- технический регламент;
- страна происхождения;
- группа продукции.

Например, если пользователь явно указал, что нужна декларация со статусом “Действует”, то документы с таким типом и статусом должны получить дополнительный вес.

#### Итоговая оценка

Итоговая оценка может рассчитываться как взвешенная сумма:
```
final_score = keyword_score * W1 + vector_score * W2 + metadata_score * W3
```
Где `W1`,`W2`,`W3` — веса отдельных компонентов.

В MVP веса могут быть заданы вручную и затем уточняться экспериментально.

Пример начальных приоритетов:

- точное совпадение номера документа имеет наибольший вес;
- совпадение по ИНН или ОГРН имеет высокий вес;
- совпадение по статусу и типу документа повышает итоговую оценку;
- семантическая близость важна для запросов по описанию продукции;
- при отсутствии номера документа vector_score становится более значимым.
### Пример ранжирования

Пользователь вводит:
```
действующая декларация на детскую одежду ООО Ромашка
```
Система выделяет признаки:
```
document_type = declaration
status = Действует
text_query = детская одежда ООО Ромашка
```
Поисковый модуль:

1. Ищет документы со статусом “Действует”.
2. Ищет декларации.
3. Ищет совпадения по заявителю.
4. Выполняет семантический поиск по продукции.
5. Объединяет результаты.
6. Сортирует по final_score.

Документ, у которого совпали статус, тип документа, заявитель и описание продукции, должен оказаться выше документа, который похож только по описанию товара.
## 6.6. Формирование контекста для RAG
RAG-модуль используется для объяснения найденных результатов.

Он не выполняет поиск самостоятельно. Для получения данных RAG-модуль обращается к `SearchService`.

Общая схема:

1. Пользователь задаёт вопрос.
2. SearchService находит top-k документов.
3. RagService получает найденные документы.
4. RagService формирует контекст для LLM.
5. LLM формирует объяснение на основе переданного контекста.
### Какие документы передаются в RAG

В LLM не передаётся вся база данных. В контекст попадают только несколько наиболее релевантных документов.

Например:
```
top-3
top-5
top-10
```
Для MVP достаточно передавать top-3 или top-5 документов.

Это снижает:

- объём prompt;
- стоимость запроса к LLM;
- риск путаницы в ответе;
- вероятность использования нерелевантных данных.
### Какие поля передаются в контекст

В контекст RAG передаются только важные поля документа:

- id документа;
- тип документа;
- номер документа;
- статус;
- дата регистрации;
- срок действия;
- заявитель;
- ИНН заявителя;
- изготовитель;
- ИНН изготовителя;
- описание продукции;
- торговая марка;
- модель;
- артикул;
- коды продукции;
- технические регламенты;
- score;
- source_url, если есть.

Пример контекста:
```
Документ 1:
id: 125
тип документа: декларация
номер: ЕАЭС N RU Д-CN.РА01.В.12345/23
статус: Действует
заявитель: ООО Ромашка
изготовитель: Example Manufacturing Co. Ltd.
продукция: одежда детская хлопковая
модель: Model A
коды продукции: 6204420000
технические регламенты: О безопасности продукции, предназначенной для детей и подростков
score: 0.91
```
### Зачем нужен контекст

Контекст нужен для того, чтобы LLM отвечала не на основе “общих знаний”, а на основе найденных документов.

То есть LLM получает ограниченный набор фактов и должна объяснить:

- какой документ найден;
- почему он может подходить;
- какие поля совпали;
- какие поля не совпали;
- что нужно проверить вручную.
## 6.7. Генерация RAG-объяснения
RAG-объяснение формируется после того, как search layer нашёл релевантные документы.

Пример вопроса пользователя:
```
Подходит ли найденная декларация для детской хлопковой одежды?
```
Система должна сформировать ответ примерно такого вида:
```
Найденный документ может соответствовать запросу, так как в описании продукции указана детская хлопковая одежда, а статус документа — “Действует”.

Совпавшие признаки:
- тип документа: декларация;
- статус: Действует;
- описание продукции: детская хлопковая одежда;
- заявитель: ООО Ромашка.

Что требует ручной проверки:
- конкретная модель товара;
- технический регламент;
- ссылка на официальный источник.

Ответ не является юридическим заключением.
```
### Структура ответа RAG

Ответ RAG должен содержать:

1. Краткий вывод.
2. Список совпавших признаков.
3. Список спорных или отсутствующих признаков.
4. Уровень уверенности.
5. Список документов-источников.
6. Предупреждение о необходимости ручной проверки.

Пример JSON-ответа:
```JSON
{
  "answer": "Документ может соответствовать запросу, так как совпадают статус, тип продукции и заявитель. Однако необходимо вручную проверить модель товара и технический регламент.",
  "confidence": "medium",
  "matched_fields": [
    "status",
    "product_full_name",
    "applicant_name"
  ],
  "manual_check_required": [
    "product_model",
    "technical_regulations",
    "source_url"
  ],
  "sources": [
    {
      "id": 125,
      "document_number": "ЕАЭС N RU Д-CN.РА01.В.12345/23",
      "document_type": "declaration",
      "status": "Действует"
    }
  ],
  "warnings": [
    "Ответ сформирован на основе найденных документов.",
    "Ответ не является юридическим заключением."
  ]
}
```
### Уровень уверенности

Уровень уверенности можно определять на основе совпадений и итогового score.

Пример:
```
high:
- точное совпадение номера документа;
- совпадение статуса;
- совпадение заявителя или ИНН;
- совпадение продукции.

medium:
- совпала продукция и часть данных заявителя;
- документ похож по смыслу, но не все поля совпали.

low:
- найдено только смысловое сходство;
- отсутствует совпадение по заявителю, модели или коду продукции.
```
Для MVP уровень уверенности может рассчитываться простыми правилами, а не сложной ML-моделью.

## 6.8. Ограничение галлюцинаций LLM
Так как в проекте используется LLM, необходимо ограничить риск галлюцинаций — ситуаций, когда модель генерирует недостоверные факты.

В данном проекте LLM используется только как объясняющий слой. Она не является источником данных.

### Основные ограничения

LLM не должна:

- выдумывать номера сертификатов или деклараций;
- утверждать, что документ существует, если он не найден в базе;
- изменять статус документа;
- придумывать заявителя, изготовителя или срок действия;
- делать юридическое заключение;
- ссылаться на документы, которых нет в sources;
- утверждать применимость документа без проверки ключевых полей.
### Правила prompt-а

В prompt для LLM должны быть явно указаны правила:

1. Отвечай только на основе переданного контекста.
2. Если данных недостаточно, прямо скажи об этом.
3. Не выдумывай документы, номера, статусы и сроки действия.
4. Не делай юридическое заключение.
5. Всегда указывай, какие поля совпали.
6. Всегда указывай, что требует ручной проверки.
7. Используй только документы из списка sources.
### Пример системной инструкции для LLM
```
Ты — помощник для анализа найденных сертификатов и деклараций соответствия.
Ты не являешься юридическим экспертом.
Отвечай только на основе документов, переданных в контексте.
Если в контексте нет подходящих документов, скажи, что данных недостаточно.
Не выдумывай номера документов, статусы, заявителей, изготовителей и сроки действия.
Всегда указывай, какие поля совпали с запросом пользователя, а какие требуют ручной проверки.
```
### Поведение при отсутствии документов

Если поиск не нашёл документы, RAG-модуль не должен обращаться к LLM для выдумывания ответа.

Правильный ответ системы:
```
{
  "answer": "По вашему запросу не найдено документов, достаточных для объяснения.",
  "confidence": "low",
  "sources": [],
  "warnings": [
    "Система не нашла релевантных документов.",
    "Попробуйте уточнить номер документа, заявителя или описание продукции."
  ]
}
```
## 6.9. Логирование поисковых запросов
Логирование необходимо для отладки, анализа качества поиска и последующей оценки результатов.

В системе используются таблицы:
```
search_logs
search_log_results
```
### Что сохраняется в search_logs

В таблицу `search_logs` сохраняется общая информация о запросе:

- исходный запрос пользователя;
- нормализованный запрос;
- режим поиска;
- применённые фильтры;
- количество найденных результатов;
- время выполнения поиска;
- признак использования RAG;
- дата и время запроса.
### Что сохраняется в search_log_results

В таблицу `search_log_results` сохраняются документы, попавшие в выдачу:

- id поискового запроса;
- id найденного документа;
- позиция документа в выдаче;
- keyword_score;
- vector_score;
- final_score;
- поля, по которым произошло совпадение.
### Зачем нужно логирование

Логирование помогает:

1. Проверять корректность работы поиска.
2. Анализировать, какие запросы приводят к хорошим результатам.
3. Находить запросы, по которым система ничего не нашла.
4. Сравнивать keyword search, vector search и hybrid search.
5. Рассчитывать метрики качества поиска.

Примеры метрик, которые можно оценивать на основе логов:

- Precision@k;
- MRR;
- среднее время выполнения запроса;
- доля запросов без результатов;
- доля запросов, где был использован RAG.

## 6.10 Итог по главе
В системе используется гибридный подход к поиску, который объединяет преимущества классического и семантического поиска.
Классический поиск хорошо подходит для точных данных: номеров документов, ИНН, ОГРН, статусов и типов документов. Семантический поиск помогает находить документы по описанию продукции на естественном языке. Гибридное ранжирование объединяет результаты этих подходов и позволяет повысить релевантность выдачи.
RAG-модуль используется только после выполнения поиска. Он не создаёт новые факты, а объясняет найденные документы на основе переданного контекста. Такой подход делает систему более понятной для пользователя и снижает риск недостоверных ответов.

# 7. Тестирование и оценка качества

## 7.1. Цель тестирования
Тестирование необходимо для проверки корректности работы основных модулей системы и оценки качества поиска документов.

Так как проект реализуется в формате MVP, тестирование должно быть направлено не на полное промышленное покрытие всех возможных случаев, а на проверку ключевых сценариев:

- импорт данных из CSV-файлов;
- сохранение документов в базе данных;
- нормализация пользовательских запросов;
- классический поиск;
- семантический поиск;
- гибридное ранжирование;
- получение карточки документа через API;
- формирование RAG-объяснения;
- работа MCP-инструментов;
- логирование поисковых запросов.

Основная цель тестирования — убедиться, что система может принять данные из открытых наборов Росаккредитации, сохранить их в базу, найти релевантные сертификаты и декларации по пользовательскому запросу и объяснить результат на основе найденных документов.

В рамках MVP допускается сочетание нескольких видов проверки:

1. Unit-тестирование отдельных функций.
2. Интеграционное тестирование модулей.
3. Ручное тестирование через Swagger UI.
4. Проверка качества поиска на заранее подготовленных запросах.
## 7.2. Тестирование импорта данных
Модуль импорта является одним из базовых компонентов системы. Если данные некорректно загружаются или сохраняются, дальнейший поиск и RAG-объяснение работать не смогут.

Тестирование импорта должно проверять, что система корректно читает CSV-файлы, преобразует строки в объекты документов и сохраняет их в базу данных.

### Проверяемые функции

При тестировании импорта проверяются следующие функции:

- чтение CSV-файла;
- обработка заголовков колонок;
- преобразование строк в внутреннюю модель документа;
- нормализация дат;
- обработка пустых значений;
- сохранение исходной строки в raw_data;
- формирование search_text;
- создание записи import_batches;
- подсчёт обработанных и ошибочных строк;
- продолжение импорта при ошибке в отдельной строке.

### Примеры тестовых случаев
| № | Проверка                                  | Ожидаемый результат                                                  |
| - | ----------------------------------------- | -------------------------------------------------------------------- |
| 1 | Импорт корректного CSV-файла деклараций   | В базе появляются документы с типом `declaration`                    |
| 2 | Импорт корректного CSV-файла сертификатов | В базе появляются документы с типом `certificate`                    |
| 3 | CSV содержит пустые поля                  | Импорт не падает, пустые значения сохраняются как `NULL`             |
| 4 | В строке некорректная дата                | Ошибка строки логируется, импорт остальных строк продолжается        |
| 5 | CSV содержит специфичные поля             | Полная исходная строка сохраняется в `raw_data`                      |
| 6 | Импорт завершён успешно                   | В `import_batches` сохраняется статус `completed`                    |
| 7 | При импорте возникла критическая ошибка   | В `import_batches` сохраняется статус `failed` и сообщение об ошибке |
---
### Критерии успешности
Импорт считается корректным, если:

- тестовый CSV-файл успешно читается;
- документы сохраняются в таблицу registry_documents;
- тип документа определяется правильно;
- основные поля документа заполняются корректно;
- исходные данные сохраняются в raw_data;
- формируется search_text;
- информация об импорте сохраняется в import_batches;
- ошибка отдельной строки не останавливает весь импорт.
## 7.3. Тестирование нормализации запросов
Нормализация запроса влияет на качество поиска. Пользователь может вводить запрос в свободной форме, поэтому система должна приводить его к виду, удобному для обработки.

### Проверяемые функции

При тестировании нормализации проверяются:

- удаление лишних пробелов;
- приведение текста к единому регистру;
- выделение возможного номера документа;
- выделение типа документа;
- выделение статуса;
- обработка похожих символов кириллицы и латиницы;
- выделение текстовой части для поиска по продукции;
- сохранение исходного и нормализованного запроса в лог.

### Примеры тестовых случаев
| № | Исходный запрос                         | Ожидаемый результат                                   |
| - | --------------------------------------- | ----------------------------------------------------- |
| 1 | `детская одежда`                        | `text_query = "детская одежда"`                       |
| 2 | `  Детская   одежда  `                  | лишние пробелы удалены                                |
| 3 | `ЕАЭС N RU Д-CN.РА01.В.12345/23`        | выделен кандидат номера документа                     |
| 4 | `действующая декларация детская одежда` | определены тип `declaration` и статус `Действует`     |
| 5 | `сертификат ООО Ромашка`                | определён тип `certificate`, выделена текстовая часть |
| 6 | `12345/23`                              | запрос используется как фрагмент номера документа     |
| 7 | `ЕАЭС N RU D-CN.PA01.B.12345/23`        | выполнена частичная нормализация похожих символов     |
---

### Критерии успешности
Нормализация считается корректной, если:

- запрос не теряется при обработке;
- лишние пробелы и регистр не влияют на поиск;
- возможный номер документа выделяется отдельно;
- текстовая часть запроса остаётся пригодной для keyword и vector search;
- система корректно обрабатывает частичные номера документов;
- нормализованный запрос сохраняется в search_logs.
## 7.4. Тестирование поиска
Поиск является ключевой функцией системы. Тестирование должно проверить работу трёх режимов:

1. Классический поиск.
2. Семантический поиск.
3. Гибридный поиск.
### 7.4.1. Тестирование классического поиска
Классический поиск проверяется на запросах, где ожидается точное или частичное совпадение.

Проверяемые сценарии:

- поиск по полному номеру документа;
- поиск по фрагменту номера;
- поиск по заявителю;
- поиск по изготовителю;
- поиск по ИНН или ОГРН;
- поиск по статусу;
- поиск по типу документа;
- поиск по коду продукции.

Примеры:
| № | Запрос                      | Ожидаемый результат                       |
| - | --------------------------- | ----------------------------------------- |
| 1 | полный номер декларации     | нужная декларация находится в top-1       |
| 2 | фрагмент номера             | нужный документ находится в top-5         |
| 3 | название заявителя          | возвращаются документы этого заявителя    |
| 4 | ИНН заявителя               | возвращаются документы с указанным ИНН    |
| 5 | `document_type=certificate` | возвращаются только сертификаты           |
| 6 | `status=Действует`          | возвращаются только действующие документы |
### 7.4.2. Тестирование семантического поиска
Семантический поиск проверяется на запросах, где пользователь вводит описание товара обычными словами.

Проверяемые сценарии:

- поиск по описанию продукции;
- поиск по близким по смыслу формулировкам;
- поиск без точного совпадения слов;
- поиск по товарной категории.

Примеры:
| № | Запрос                     | Ожидаемый результат                      |
| - | -------------------------- | ---------------------------------------- |
| 1 | `товары для малышей`       | находятся документы по детской продукции |
| 2 | `верхняя одежда для детей` | находятся документы по одежде для детей  |
| 3 | `косметическая продукция`  | находятся документы по косметике         |
| 4 | `молочная продукция`       | находятся документы по молочным товарам  |

Семантический поиск считается корректным, если он возвращает документы, близкие по смыслу к запросу, даже если в них используются другие формулировки.
### 7.4.3. Тестирование гибридного поиска
Гибридный поиск проверяется на смешанных запросах, где присутствует несколько признаков.

Пример запроса:
```
действующая декларация на детскую одежду ООО Ромашка
```
Система должна учесть:

- тип документа: декларация;
- статус: действует;
- описание продукции: детская одежда;
- организацию: ООО Ромашка.

Примеры тестовых случаев:
| № | Запрос                                  | Ожидаемый результат                                       |
| - | --------------------------------------- | --------------------------------------------------------- |
| 1 | `действующая декларация детская одежда` | выше ранжируются действующие декларации по детской одежде |
| 2 | `сертификат одежда для детей`           | выше ранжируются сертификаты по детской продукции         |
| 3 | `ООО Ромашка косметика`                 | выше документы с совпадением по организации и продукции   |
| 4 | `12345/23 детская одежда`               | документ с совпадением номера выше семантически похожих   |
| 5 | `архивный сертификат мебель`            | учитывается статус и тип документа                        |

### Критерии успешности поиска
Поиск считается работающим, если:

- точное совпадение номера попадает в top-1;
- частичное совпадение номера попадает в top-5;
- поиск по заявителю возвращает документы этого заявителя;
- поиск по описанию продукции возвращает смысловые совпадения;
- гибридный поиск учитывает и фильтры, и semantic similarity;
- результаты содержат score или позицию в выдаче;
- поисковые запросы сохраняются в search_logs и search_log_results.
## 7.5. Тестирование API
API тестируется для проверки доступности endpoint-ов, корректности форматов запросов и ответов, а также обработки ошибок.

### Проверяемые endpoint-ы

Для MVP проверяются следующие endpoint-ы:
```
GET /health
GET /documents/{document_id}
GET /documents
POST /search
POST /rag/ask
POST /admin/imports
GET /admin/imports/{import_id}
```
### Примеры тестов API
| Endpoint              | Проверка                        | Ожидаемый результат             |
| --------------------- | ------------------------------- | ------------------------------- |
| `GET /health`         | сервис запущен                  | возвращается `{"status": "ok"}` |
| `GET /documents/{id}` | документ существует             | возвращается карточка документа |
| `GET /documents/{id}` | документ не существует          | возвращается ошибка 404         |
| `GET /documents`      | запрос с пагинацией             | возвращается список документов  |
| `POST /search`        | корректный поисковый запрос     | возвращается список результатов |
| `POST /search`        | пустой запрос                   | возвращается ошибка 400         |
| `POST /rag/ask`       | вопрос с найденными документами | возвращается ответ и sources    |
| `POST /admin/imports` | корректный файл                 | запускается импорт              |

### Критерии успешности API
API считается корректным, если:

- endpoint-ы доступны через Swagger UI;
- ответы возвращаются в формате JSON;
- успешные запросы возвращают ожидаемые данные;
- ошибки возвращаются в едином формате;
- несуществующие документы возвращают 404;
- некорректные параметры возвращают 400 или 422;
- RAG endpoint возвращает sources и предупреждения.
## 7.6. Тестирование RAG-ответов
RAG-модуль тестируется отдельно, потому что он использует LLM и может формировать текстовые ответы.

Главная задача тестирования RAG — убедиться, что LLM объясняет найденные документы, но не выдумывает новые факты.

### Проверяемые свойства RAG-ответа

RAG-ответ должен:

- основываться только на найденных документах;
- содержать краткий вывод;
- указывать совпавшие поля;
- указывать поля, требующие ручной проверки;
- содержать документы-источники;
- предупреждать, что ответ не является юридическим заключением;
- корректно отвечать при недостатке данных.

### Примеры тестовых случаев
| № | Ситуация                                               | Ожидаемый результат                                    |
| - | ------------------------------------------------------ | ------------------------------------------------------ |
| 1 | Найден документ с совпадением по продукции и заявителю | RAG указывает совпавшие поля                           |
| 2 | Найден похожий документ, но модель товара не совпадает | RAG сообщает о необходимости ручной проверки           |
| 3 | Документы не найдены                                   | RAG не выдумывает ответ и сообщает о недостатке данных |
| 4 | Документ имеет статус `Архивный`                       | RAG не называет его действующим                        |
| 5 | В источниках нет данных о производителе                | RAG не придумывает производителя                       |
| 6 | Пользователь просит юридическое заключение             | RAG отвечает, что система не заменяет эксперта         |

### Критерии успешности RAG
RAG считается корректным, если:

- ответ не содержит фактов, отсутствующих в sources;
- статус документа передаётся без изменений;
- номер документа не искажается;
- в ответе есть предупреждение о ручной проверке;
- при отсутствии документов система не формирует ложное объяснение;
- sources соответствуют документам, использованным в ответе.
## 7.7. Тестирование MCP tools
MCP tools тестируются для проверки взаимодействия LLM-клиента с сервисом.

В MVP проверяются три инструмента:
```
search_registry
get_document_card
explain_match
```
### Тестирование search_registry

Проверяется, что инструмент принимает текстовый запрос и возвращает список найденных документов.

Пример входных данных:
```JSON
{
  "query": "детская одежда ООО Ромашка",
  "document_type": "declaration",
  "limit": 5
}
```
Ожидаемый результат:

- инструмент возвращает список документов;
- каждый документ содержит id, номер, статус и краткое описание;
- результат соответствует логике SearchService.

### Тестирование get_document_card
Проверяется, что инструмент возвращает карточку документа по id или номеру.

Ожидаемый результат:

- существующий документ возвращается корректно;
- несуществующий документ возвращает понятную ошибку;
- карточка содержит основные поля документа.
### Тестирование explain_match
Проверяется, что инструмент формирует объяснение применимости документа к запросу пользователя.

Ожидаемый результат:

- инструмент использует RagService;
- ответ содержит sources;
- ответ не содержит выдуманных данных;
- инструмент не изменяет данные в базе.
### Критерии успешности MCP

MCP-инструменты считаются корректными, если:

- запускается MCP server;
- инструменты доступны LLM-клиенту;
- инструменты используют service layer;
- инструменты работают только на чтение;
- инструменты не выполняют произвольный SQL;
- результаты совпадают с результатами соответствующих REST API.
## 7.8. Метрики качества поиска
Для оценки качества поиска используются простые метрики, подходящие для MVP.

Метрики нужны, чтобы оценивать систему не только по принципу “работает/не работает”, но и по качеству выдачи.
### 7.8.1. Precision@k

`Precision@k` показывает, какая доля документов в первых `k` результатах является релевантной.

Формула:
```
Precision@k = количество релевантных документов в top-k / k
```
Пример:
```
Пользовательский запрос: детская одежда
top-5 содержит 3 релевантных документа

Precision@5 = 3 / 5 = 0.6
```
Эта метрика полезна, потому что пользователь обычно смотрит первые несколько результатов выдачи.
### 7.8.2. MRR

`MRR` означает Mean Reciprocal Rank.

Эта метрика показывает, насколько высоко в выдаче находится первый правильный документ.

Для одного запроса:
```
Reciprocal Rank = 1 / позиция первого релевантного документа
```
Пример:
```
Если первый релевантный документ находится на 1 позиции:
RR = 1 / 1 = 1

Если первый релевантный документ находится на 3 позиции:
RR = 1 / 3 = 0.33
```
MRR считается как среднее значение Reciprocal Rank по набору тестовых запросов.

Эта метрика полезна для оценки того, насколько быстро пользователь видит нужный документ.
### 7.8.3. Search latency

`Search latency` показывает время выполнения поискового запроса.

Для MVP можно измерять:

- время классического поиска;
- время семантического поиска;
- время гибридного поиска;
- общее время ответа API.

Пример целевого значения для MVP:

- обычный поиск: до 1–2 секунд;
- семантический поиск: до 2–5 секунд на тестовой выборке;
- RAG-ответ может выполняться дольше из-за обращения к LLM.
### 7.8.4. Zero results rate

`Zero results rate` показывает долю запросов, по которым система ничего не нашла.

Формула:
```
Zero results rate = количество запросов без результатов / общее количество запросов
```
Если доля запросов без результатов слишком высокая, это может означать, что:

- нормализация работает недостаточно хорошо;
- поиск слишком строгий;
- данных в базе недостаточно;
- embedding-модель плохо подходит для предметной области.
## 7.9. Набор тестовых сценариев
Для оценки MVP формируется небольшой набор тестовых запросов.

Он должен включать разные типы пользовательского ввода:

- точный номер документа;
- фрагмент номера;
- название организации;
- ИНН или ОГРН;
- описание продукции;
- смешанный запрос;
- запрос без ожидаемого результата.
### Пример набора тестовых сценариев
| №  | Запрос                                    | Проверяемый механизм            | Ожидаемый результат                            |
| -- | ----------------------------------------- | ------------------------------- | ---------------------------------------------- |
| 1  | Полный номер декларации                   | классический поиск              | документ находится в top-1                     |
| 2  | Фрагмент номера сертификата               | классический поиск              | документ находится в top-5                     |
| 3  | `ООО Ромашка`                             | поиск по организации            | документы организации отображаются в выдаче    |
| 4  | `детская одежда`                          | semantic / hybrid search        | находятся документы по детской продукции       |
| 5  | `действующая декларация детская одежда`   | hybrid search                   | выше ранжируются действующие декларации        |
| 6  | `сертификат верхняя одежда дети`          | hybrid search                   | выше ранжируются сертификаты по детской одежде |
| 7  | `товары для малышей`                      | semantic search                 | находятся смыслово близкие документы           |
| 8  | `несуществующий номер 000000`             | обработка отсутствия результата | система сообщает, что документов не найдено    |
| 9  | `архивный сертификат мебель`              | фильтрация по статусу и типу    | учитываются статус и тип документа             |
| 10 | `подходит ли документ для детской одежды` | RAG                             | ответ содержит объяснение и sources            |
---

### Разметка релевантности

Для расчёта метрик качества нужно заранее определить, какие документы считаются релевантными для каждого тестового запроса.

В MVP это можно сделать вручную:

1. Подготовить 10–20 тестовых запросов.
2. Для каждого запроса вручную указать ожидаемые документы.
3. Запустить поиск.
4. Сравнить top-k выдачу с ожидаемыми результатами.
5. Рассчитать Precision@k и MRR.

Такой подход подходит для учебного проекта, так как не требует большого размеченного датасета.
## 7.10. Ограничения тестирования MVP
Тестирование MVP имеет ограничения, связанные с учебным характером проекта и ограниченной выборкой данных.

Основные ограничения:

- тестирование проводится на ограниченном наборе документов;
- тестовые запросы подготавливаются вручную;
- релевантность документов оценивается вручную;
- RAG-ответы частично оцениваются экспертно или вручную;
- не проводится полноценное нагрузочное тестирование на полном объёме открытых данных;
- не проверяется юридическая применимость документа к конкретному товару;
- автоматический импорт по расписанию может быть не включён в MVP;
- качество embeddings зависит от выбранной модели.

Важно, что система не заменяет специалиста по сертификации. Поэтому тестирование RAG-ответов направлено не на проверку юридической истинности выводов, а на проверку того, что объяснение основано на найденных документах и не содержит выдуманных фактов.
